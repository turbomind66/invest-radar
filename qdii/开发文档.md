# QDII 海外基金定投决策面板 — 开发文档

> 状态：架构与可行性已确认（评审通过即进入开发）
> 目标仓库：`invest-radar`（已更名，原 `national_team_tracker`；GitHub 仓库同步更名）。同一 Docker Compose 部署，一个 `docker compose up` 同时拉起「国家队 A 股日报」与「QDII 定投决策面板」两套服务。
> 技术栈：零第三方 Python 依赖（标准库）+ 东方财富/天天基金数据源 + ECharts（CDN）+ 静态站/API 展示，与现有 tracker 完全一致

---

## 1. 项目目标与范围

构建一个面向**场外 QDII 指数基金**的定投决策面板，回答两个问题：

1. **能不能买** —— 基金当前是否开放申购、每日限额多少、各平台（基金公司/天天基金/支付宝/券商）的申赎规则与费率差异。
2. **划不划算** —— 每日 14:30（北京时间）抓取美股信号（标普500/纳斯达克100 现货+期货、美债），结合「跟跌加仓 + 固定周期 + 信号增强 + 估值百分位 + 避险情绪」策略，输出每只基金的「建议投入倍数」。

附加：每只基金的**跟踪误差**（跟不跟得住指数），作为「是否适合无脑定投」的参考；以及**对应场内基金的溢价率**（同一标的在场内/场外两个渠道的价差，直接决定从哪个口子买更划算，也是限购抢手程度的信号）。

### 1.1 不在范围内（本期不做）
- 券商逐笔费率抓取（券商分散、需各自登录态，难度高）；本期券商只标记「是否代销」。
- 自动下单/代客交易（系统只给信号与建议，下单由用户手动完成）。
- 实时Tick级行情（14:30 抓一次日级/分钟级快照即可）。

## 2. 总体架构

### 2.1 部署架构（同 Compose，零耦合）

在现有 `national_team_tracker` 镜像内新增 `qdii/` 子模块，新增两个容器服务，与现有 `web`/`cron` 并列，**共用同一个 `ntt-data` 卷但使用独立 DB 文件**，互相不抢写锁：

| 服务 | APP_ROLE | 进程 | 端口(容器内) | 宿主机 | DB |
|------|----------|------|-------------|--------|-----|
| ntt-web（现有） | web | app.py | 5000 | 18080 | data.db |
| ntt-cron（现有） | cron | scheduler.py | — | — | data.db |
| **qdii-web（新增）** | qdii-web | qdii/app.py | 5001 | 18081 | qdii.db |
| **qdii-cron（新增）** | qdii-cron | qdii/scheduler.py | — | — | qdii.db |

- `docker compose up -d --build` 一次拉起 4 个容器。
- 访问 `18080` 看国家队、`18081` 看 QDII，互不影响。
- 两个 DB 各自文件锁（锁路径不同），无并发冲突。

## 3. 功能模块划分与开发细节

### 3.1 模块 A —— 基金池管理（`fetcher_pool.py` + `constants.py` + 表 `qdii_fund`）

**目标**：维护一份确定的「目标基金池」——覆盖标普500 / 纳斯达克100 / 日经225 / 德国DAX（及可选的法国CAC、英国富时、印度、越南）的**场外**联接/LOF 基金。

**开发细节**：
1. `constants.py` 内维护手工清单 `FUND_POOL`：每项 `{code, name, index, category, company, fund_type}`。
   - 过滤规则（参考 `promise96319/qdii`）：排除纯场内 ETF 代码前缀 `15/51/52/56/58`；**保留 `16` 开头 LOF**（场外可申购，如 161130 易方达纳指100、161125 易方达标普500）。
   - 排除美元份额（名称含 美元/美汇/美钞/现汇/现钞）。
2. 可选增强：用 `https://fund.eastmoney.com/js/fundcode_search.js`（全市场代码名）做名称匹配「标普500/纳指100/日经225/德国DAX」自动补全候选，再人工确认入池。
3. 建表 `qdii_fund`（种子数据一次性写入），后续只增不减。

**初始候选池（示例，开发时补全）**：
- 标普500：博时 050025、易方达 161125、天弘 007721、大成 096001…
- 纳斯达克100：国泰 160213、广发 270042、大成 000834、易方达 161130、华安 040046…
- 日经225：华夏野村日经225ETF联接、易方达日兴资管日经225、华安三菱日联日经225…
- 德国DAX：华安德国30(DAX)ETF联接 000614、嘉实德国DAXETF联接 000614 同类…

### 3.2 模块 B —— 申购状态 + 限额追踪（`fetcher_limit.py` + 表 `qdii_limit_status`）

**目标**：每日抓取每只基金的申购状态（开放/暂停/限大额）、单日累计限定金额、下一开放日、购买起点、赎回状态。

**数据源（天天基金，无需鉴权，均已实测可达）**：
- 全量申购状态/限额表（AKShare `fund_purchase_em` 同源稳定接口）：`https://fund.eastmoney.com/Data/Fund_JJJZ_Data.aspx?t=8&page=1,50000&js=reData&sort=fcode,asc`，返回 `var reData={datas:[...]}`。
  字段顺序：`[代码, 简称, 类型, 最新净值, 净值日期, 申购状态, 赎回状态, 下一开放日, 购买起点, 日累计限定金额, ?, ?, 手续费]`；`日累计限定金额` 为 `1e11` 量级表示「不限」。已实测返回 2.9MB 全量，**比 HTML 页更稳**（HTML 页 `Fund_sgzt_bzdm.html` 为 gb2312、易随改版变动，仅作兜底）。
- 单基金明细/费率（补充）：`https://fundmobapi.eastmoney.com/FundMApi/FundRateInfo.ashx?FCODE=CODE&deviceid=1&plat=Android&product=EFund&version=6.5.5`（**必须带 deviceid 等参数**，否则返回异常）。返回 JSON：`SGZT`(开放申购/限大额/暂停申购)、`MAXSG`(单日累计限额元)、`MINSG`/`MINDT`、`MGREXP`/`TRUSTEXP`/`SALESEXP`(管理/托管/销售服务费 %/年)、`sg[]`(申购费阶梯 source原价/rate折后)、`sh[]`(赎回费阶梯 time持有期限/rate费率)、`SSBCFMDATA`(申购确认 T+N)。已实测 161125 → `SGZT=暂停申购, MAXSG=10, MGREXP=0.80%, TRUSTEXP=0.20%`。

**⚠️ 编码：必须是 UTF-8，不能按 GBK 解码（2026-10-29 实测踩坑）**：
`Fund_JJJZ_Data.aspx` 返回的是 **UTF-8 字节**。若误用 GBK 解码**不会抛异常**（GBK 几乎不触发 `UnicodeDecodeError`，因此 common/http.py 的 GBK 降级分支也不会生效），只会静默产生乱码（`暂停申购` → `鏆傚仠鐢宠喘`）。
后果：状态归一化函数匹配不到「暂停」关键字，`暂停申购` 被误判为 `OPEN`，**把买不了的基金推荐成可买**。数值字段（代码/限额/购买起点）不受编码影响，故障极具隐蔽性。
验证方式：同一接口分别以 utf-8 / gbk 解码，对比 `[1]`(名称) 与 `[5]`(申购状态) 是否为正常中文。

**开发细节**：
1. `fetch_all_limit_status()`：拉全量表（**UTF-8 解码**）→ 按 `FUND_POOL` 代码过滤 → 写 `qdii_limit_status`（按 date 分区，UPSERT）。
2. 字段映射：`日累计限定金额` 为 `1e11` 量级表示「不限」，需归一化为「限额(元)」与「是否限额」布尔（阈值 `LIMIT_UNLIMITED_THRESHOLD=1e10`）。
3. `申购状态` 归一为枚举：`OPEN`(开放) / `SUSPEND`(暂停) / `LIMIT`(限大额)。
4. 历史序列：每日一行，前端可画「某基金限购何时从不限→1000元→暂停」的时间线。

**实测结果（2026-10-29）**：11 只基金中 **7 只 SUSPEND、4 只 LIMIT**（日限额 5～1000 元），与 QDII 外汇额度紧张的现实一致；支付宝侧状态与之完全吻合（双源交叉验证通过）。

### 3.3 模块 C —— 多平台申赎规则 + 费率矩阵（`fetcher_fee.py` + 表 `qdii_platform_fee`）

**目标**：以「基金 × 平台」矩阵展示：在售状态、单日限额、申购费(原价/折后)、赎回费阶梯、销售服务费、管理费、托管费、免赎回费天数、定投状态、大额限购。平台列：**基金公司(基准限购)** / **天天基金** / **支付宝** / **理财通** / **券商**。

**数据源**：
- 基金公司基准限购：来自模块 B 的 `qdii_limit_status`（基金公司设定，各代销渠道统一）→ 作为矩阵「基金公司」列与权威性基准。
- 天天基金：模块 B 的 `FundRateInfo.ashx` 已含申购费/赎回费阶梯/销售服务费/管理费/托管费/定投状态/大额限购。
- 支付宝(蚂蚁基金)：在售状态取 `https://www.fund123.cn/matiaria?fundCode=CODE`（服务端渲染，无需设备号）。解析 `<script>` 内 `window.context.materialInfo.fundBrief.saleStatus`（取值：正常申购/暂停销售/不可售）。已实测 161125 页面返回 200 且 `window.context` 存在、含 `materialInfo`。⚠️ 支付宝**申购费折后价无法获取**（页面坏字段，与参考项目 `promise96319/qdii` 结论一致），折后价仍以天天基金口径展示并注明「平台折扣以实际下单页为准」。
- **理财通**：⚠️ 2026-10-29 实测 **无公开接口**——网页版 `fund.qq.com` / `licai.qq.com` 已下线（DNS 都解析不到），服务只在微信 App 内、且需登录态，因此无法逐只抓取。按**平台通用规则推算**并显式标注，不伪装成实时抓取：
  - 管理费 / 托管费：基金合同约定，全平台一致 → 直接沿用同一基金的值；
  - 申购费：理财通 A 类长期 **1 折**（促销期可 0 元购）→ 原费率 × 0.1；
  - 申购状态：跟随基金公司限购公告（与天天基金同源）；
  - 起购金额：按常见 **10 元**；
  - 落库 `source = 'rule:licai'`，前端据此渲染灰色「推算」徽标，并在区块说明里写清推算依据。
- 券商：本期**只标记「是否代销」**（由各券商公开基金超市或基金池已知代销渠道核对），不做费率抓取。

**开发细节**：
1. `fetch_platform_fee()`：循环 `FUND_POOL` → 天天基金费率 + 支付宝在售/折扣 → 写 `qdii_platform_fee`（platform 字段区分）。
2. 费用计算辅助：`年费 = 管理费 + 托管费 + 销售服务费`，前端排序默认「可申购优先 → 限额高→低 → 年费低→高 → 代码升序」（参考 promise96319/qdii）。
3. 赎回费阶梯存 JSON（如 `{"<7天":1.5%,"7~30天":0.5%,">30天":0%}`）。
4. **行合并口径（2026-10-29）**：页面按「一只基金一行块」展示——`代码` + `基金名称` 两列用 `rowspan` 纵向合并，右侧再跟 天天基金 / 支付宝 / 理财通 各一行，同一只基金只显示一次代码与名称。
   前置条件：`get_platform_fee()` 必须保证**同代码相邻 + 平台顺序固定**。原实现没有 `ORDER BY`，行序是 SQLite 物理存储序，合并会错行；
   而改 `ORDER BY code` 又会把 `FUND_POOL` 的大类顺序（标普500 → 纳指100 → 日经225 → 德国DAX）打乱，所以改为在 Python 里按 `FUND_POOL` 下标 + 平台秩排序（测试 `PlatformFeeOrderTest` 守着）。
5. **与模块 B 合并成一张表（`board.py`，2026-10-29）**：模块 B（申购状态/限额）与模块 C（多平台费率）原来各占一张表，两张表都有「代码/名称」，同一只基金要来回对代码才能判断「还能不能买 + 在哪个平台买便宜」。现由 `board.py` 在服务端按 `code` 做 join，输出 `/api/qdii/board`：
   - **一只基金一个块**：基金级字段（代码/名称/类别/申购状态/日限额/下一开放日/起购）`rowspan=N` 纵向合并，右侧跟 N 行平台数据（平台 / 在售 / 申购费「原→折」）。
   - **固定年费（管理费/托管费/销售服务费/年费合计）提到基金级**：这三项是**基金合同条款，任何平台都一样**，逐平台重复三遍既占宽度又容易让人误以为平台间有差异——真正按平台变的只有「在售」和「申购费」。
   - 「限大额但单日 < 100 元」标 **变相暂停** 徽标，阈值与 `strategy` 的 100 元口径一致（否则表头说「限大额」、决策理由说「等同变相暂停」，自相矛盾）。
   - 合并逻辑是纯函数 `merge_board(limit_rows, fee_rows, pool)`，不碰数据库，便于单测（`BoardMergeTest` 6 项）；没有费率行只有状态行的基金也会出现（否则「暂停且抓不到费率」的基金会凭空消失）。
   - 原始接口 `/api/qdii/limit`、`/api/qdii/fee` 保留，排障与追溯用。
6. **表头排序（2026-10-29）**：两段式排序，**在后端做**（口径唯一、可单测），前端只传列键：
   - **基金级**（`sort` 参数）：类别 / 申购状态 / 日限额 / 下一开放日 / 起购 / 管理费 / 托管费 / 销售服务费 / 年费合计 → 改变**哪只基金排在前面**。
   - **平台级**（`psort` 参数）：平台 / 在售 / 申购费 → 只改变**同一只基金内部各平台行的先后**，**各基金之间的顺序完全不变**（丁总口径）。
   - 排序规则细节：类别按 `FUND_POOL` 的类别序（不是字符串码点，否则「日经225」会排到「标普500」前）；申购状态按 `开放 → 限大额 → 暂停`；平台按固定秩 `天天基金 → 支付宝 → 理财通`；申购费按**折后价**排；**空值恒定排最后**（不随升降序翻转，否则降序时空值会跑到最前面）；同值保持原顺序（稳定排序）。
   - 前端：表头 `th[data-sort]` / `th[data-psort]` 点击切换方向，箭头 ▲▼ 显示当前排序列；排序状态写入 URL（`?sort=…&dir=…&psort=…&pdir=…`），刷新与分享不丢状态。
   - 单测 `BoardSortTest` 8 项守口径（基金级排序、平台级排序不改变基金顺序、空值恒末、未知键不生效等）。

### 3.4 模块 D —— 每日美股信号（14:30）（`fetcher_signal.py` + 表 `qdii_us_signal`）

**目标**：每日 14:30 北京时间抓取标普500现货、纳斯达克100现货、标普500期货、纳斯达克100期货、美债10Y 的最新价与涨跌幅。

**⚠️ 关键时区事实（必须落实在页面标注）**：
- 14:30 北京时间 = 美东 ET 约 01:30–02:30 → **美股现货/美债已收盘**，抓到的是**上一交易日收盘（非实时）**；**美股期货（CME Globex 近24h）为实时**。
- 但「现货昨收涨跌幅」恰好 = QDII 本次申购将成交的净值方向（QDII T日申购按海外收盘净值，T+1/T+2 披露）；「期货实时」= 今晚开盘前瞻。

**数据源（已实测确定可行，主用「新浪期货 + 雅虎」组合，国内友好）**：
- **美股期货（实时，CME Globex 近24h）**：新浪全球期货 `https://hq.sinajs.cn/list=hf_ES,hf_NQ`（需 Referer `https://finance.sina.com.cn/`、GBK 解码）。`hf_ES`=标普500指数期货、`hf_NQ`=纳斯达克指数期货。**已实测 200 且数据真实**。新浪为现有 tracker 已用源，国内直连稳定。
  - ⚠️ **字段位置表（2026-10-29 实测 15 段，禁止凭印象改）**：`[0]` 现价、`[2]` 买价、`[3]` 卖价、`[4]` 最高、`[5]` 最低、`[6]` 时间、`[7]` **昨收**、`[8]` 开盘、`[12]` 日期、`[13]` **中文名**、`[14]` 占位 `0`。
  - 历史 bug：曾用 `parts[5]` 当价格（实际是当日**最低价**）、`parts[-1]` 当名称（实际是占位 `"0"`），导致页面出现「名称 0、价格恒为最低价、涨跌幅恒 0.00%」。现按上表解析，并用 `(现价/昨收−1)` 真实计算涨跌幅。
- **美股现货（上一交易日收盘 = 本次申购将成交净值方向）**：雅虎 `https://query1.finance.yahoo.com/v8/finance/chart/^GSPC`（标普500）、`^NDX`（纳指100）、`^IXIC`（纳指综合）。**已实测 ^GSPC/^IXIC 返回 200**；`^NDX` 经沙盒代理偶发 SSL 抖动，生产直连稳定。
- **美债10Y（情绪/宏观参考）**：雅虎 `^TNX`。**已实测 200，regularMarketPrice=5.045（即 10Y 收益率 ~5.05%）**。备选东财 push2（见下）。
- **VIX（避险情绪开关源）**：雅虎 `^VIX`。**已实测 200，=16.91**。
- ⚠️ **东财 `push2.eastmoney.com` 原方案说明**：生产环境（现有 tracker 已依赖东财 clist/push2）可直连；但**本分析沙盒无论走代理还是直连均 TCP 层被拒**，故无法在沙盒内验证其美股 secid（`100.SPX` 等标准）。生产 VPS 部署时需实测 `i:100.SPX/i:100.NDX` 及期货 secid，作为新浪/雅虎之外的备选源。当前主方案（新浪 + 腾讯）已覆盖全部标的且实测可达，无阻塞。

**开发细节**：
1. `fetch_us_signal()`：并行请求指数 + 期货 + 美债 → 写 `qdii_us_signal`（symbol/last_price/change_pct/is_realtime/as_of）。
2. `is_realtime` 字段：期货=1，现货/美债=0（前端据此标注「实时/上一交易日」）。
3. 失败降级：任一标的失败不阻断整体，缺失项前端显式标「—/暂不可用」。

### 3.5 模块 E —— 跟踪误差（`tracking_error.py` + 表 `qdii_tracking_error`）

**目标**：展示每只基金相对标的指数的跟踪误差（年化标准差），辅助判断「是否适合无脑定投」。

**数据源（2026-10-29 重做，已定稿）**：
1. **基金历史净值**：东财 `api.fund.eastmoney.com/f10/lsjz?fundCode=CODE&pageIndex=N&pageSize=20`。
   ⚠️ **该接口忽略 `pageSize`，每页固定返回 20 条**，必须按 `pageIndex` 翻页累积（实现取 8 页 ≈ 160 个交易日）。若只取首页，样本仅 20 个点，算出的 TE 无意义。
2. **基准 = 真实指数日线，不是场内 ETF**。按「新浪优先、东财兜底」配**有序候选源**（`constants.TRACK_BENCHMARK`）：

   | 指数 | 主源（新浪美股指数日K） | 备源（东财 push2his secid） | lag |
   |---|---|---|---|
   | 标普500 | `.INX` | `100.SPX` | 0 |
   | 纳斯达克100 | `.NDX` | `100.NDX100`（**不是 `100.NDX`**，后者无效） | 0 |
   | 日经225 | 无（symbol 返回 `null`） | `100.N225` | 0 |
   | 德国DAX | 无（symbol 返回 `null`） | `100.GDAXI` | 0 |

   - 新浪接口：`stock.finance.sina.com.cn/usstock/api/jsonp_v2.php/var%20_=/US_MinKService.getDailyK?symbol=.INX`，返回 JSONP，全历史（`.INX` 可回溯到 2004 年），实测稳定。
   - 东财接口在部分网络出口整族被断（`RemoteDisconnected`，见「已知限制」），故不作唯一来源。

   > **❌ 禁止用场内 ETF（如 513100）代替指数作基准**：QDII ETF 自身折溢价噪声极大（实测溢价可达 15%+），用它当日线基准会把 TE 高估到 **30%+** 的荒谬水平（已实测复现，见下）。这一条曾两次走错，务必守住；单测 `TrackingErrorTest.test_benchmark_is_true_index_not_etf` 已强制校验。

3. **⚠️ 日期对齐：lag 一律取 0（实测推翻原判断）**。原以为「QDII 净值 T+1 反映海外收盘 ⇒ 需前推 1 个交易日」，实测正好相反：东财 `lsjz` 的净值日期（FSRQ）**已对齐到海外估值日**，同交易日直接配对才对。
   - 实测（2026-10-29，160 个净值样本）：`lag=0` → 161125 **1.23%**、161130 **1.55%**、040046 **1.06%**（符合指数基金 1~3% 的常识区间）；换成 `lag=1` → **18.62% / 30.50% / 31.14%**，是纯错位造成的假偏离。
   - 结论：QDII 的「T+1」体现在**披露时间**，不是净值日期的标注。`lag` 字段保留仅为个别基金微调。
   - 合成序列校验：净值恰为「滞后 1 日指数水平」时，`lag_override=1` 算出 TE = **0.00**、`lag_override=0` 显著大于 0 —— 机制本身正确，错的是把 default 定为 1。

**⚠️ 已弃用/不可用方案（均实测）**：
- 雅虎日线（`query1.finance.yahoo.com`）→ **403 封禁**，模块 D/E 原依赖已全部移除。
- 腾讯日 K（`web.ifzq.gtimg.cn`）→ 美股指数只返 1 行；`WorldKlineController` 接口已下线（返回 `Can't load controller`）。
- 新浪全球指数历史（`GlobalIndexService.*`）→ 404 / `Service not found`；`hq.sinajs.cn/list=int_nikkei` 只有实时快照，无日线。
- 结论：**美股指数历史用新浪 `US_MinKService.getDailyK`，日经/DAX 只能靠东财 `push2his`**。

**开发细节**：
1. `compute_te(code)`：取 NAV 历史 + 指数日线 → 错位对齐 → 算日收益差 → `TE = std(diff) × √252`（百分点）。
2. 结果按 `(btype, bcode)` 做进程内缓存：11 只基金只有 4 个不重复指数基准，避免重复抓取触发限流。
3. `fetch_tracking_error()` 遍历基金池写入 `te_computed`/`as_of_date`/`benchmark`，并记录 `last_te_fetch`。
4. 前端排名：误差小的置顶（绿色），误差大的标黄提示。

**⚠️ 已知限制（2026-10-29 实测）**：
- 东财 `push2*` 主机族在**部分出口整族被断**：同一出口下 `100.SPX` 能通、`100.N225` / `100.GDAXI` 立刻 `RemoteDisconnected`，说明是链路/白名单而非参数问题。因此当前环境 **9/11 只能算出**（标普500 4 只 + 纳指100 5 只，走新浪），**日经225 与 德国DAX 暂缺**（页面显示占位，不编造数值）；换到服务器或 Actions 出口通常即恢复。
- 单只失败不影响其它基金（逐只 try/except + 幂等 UPSERT），下次调度自动补齐。
- **096001（大成标普500等权重）TE 偏高（9.09%）属真实差异**：它跟踪的是**等权重**标普500，而基准取的是市值加权 `.INX`，两者成分权重不同，年化偏离 9% 量级属正常；若要更准需找等权重指数源（新浪 `.SPXEW` / `.OEX` 实测返回 `null`，暂不可得）。

### 3.6 模块 F —— 定投决策引擎（`strategy.py` + 表 `qdii_decision`）

**目标**：结合信号与策略，输出每只基金「建议投入倍数」。

**采纳的策略组合（用户已确认）**：
- **骨架 = 固定周期+信号增强（③）**：固定每周投基准额，用信号微调当期额度。
- **加仓量依据 = 跟跌加仓（②）+ 估值百分位（④）**：跌越多/估值越低 → 倍数越高。
- **防御开关 = 避险情绪（⑤）**：美债避险信号极端时 → 临时减额。

**输入**：
- 现货昨收涨跌幅（标普500/纳指100，来自 `qdii_us_signal` 非实时项）
- 期货实时涨跌幅（同表实时项，作为今晚前瞻）
- 估值百分位（标普500/纳指100 的 PE 历史百分位；⚠️ 数据源实现时定，可用东方财富/新浪估值或静态年度百分位表）
- 美债/避险情绪（10Y 收益率变动 + VIX；VIX 数据源待定，备选东方财富/CBOE）
- 基金自身：申购状态（能否买）、限额（能买多少）、跟踪误差（是否适合）

**输出（建议倍数）示例逻辑（参数全部可配置）**：
```
倍数 = 1.0（基准）
if 现货昨收跌: 倍数 += 跌幅档位加仓（如 -2%→+0.5, -4%→+1.0, -6%→+1.5）
if 估值百分位<30%: 倍数 += 0.5（低估）
if 估值百分位>70%: 倍数 -= 0.5（高估，减额）
if 美债避险极端(risk-off): 倍数 *= 0.5（防御开关）
if 基金 SUSPEND(暂停申购): 倍数 = 0（不能买）
if 基金 LIMIT(限大额): 倍数封顶 = 限额/基准额
倍数 = clamp(倍数, 0, 上限)
```
- 提供 7 种策略档位（文档第1节已列：固定金额/跟跌/固定+信号/估值百分位/情绪/止盈/仅提示），用户可在前端切换「全自动」或「仅提示人工」。

**开发细节**：
1. `recommend(fund, signals, valuation, sentiment)` → 返回 `{multiple, reason[]}`。
2. `run_daily_decision()`：遍历 `FUND_POOL` → 写 `qdii_decision`（date/code/multiple/reason_json）。
3. 参数集中在 `constants.py`（`STRATEGY_PARAMS`），便于调参，不硬编码。

### 3.7 模块 G —— 场内溢价率监控（`fetcher_premium.py` + 表 `qdii_premium`）

**目标**：展示每只场外 QDII 基金**对应场内基金**的溢价/折价率。场外按净值申购、场内按价格交易，同一标的两条渠道的价差直接决定「从哪个口子买更划算」；同时，高溢价往往意味着该基金限购抢手（需求 > 供给），是定投决策的重要旁证信号。

**场外 ↔ 场内 映射规则（`qdii_fund.online_code`）**：
- **LOF（16 开头）**：同一代码既场外申购又场内交易 → `online_code = code`（如 161125 易方达标普500、161130 易方达纳指100）。溢价率 = 该 LOF 场内价 vs 其自身净值。
- **ETF 联接基金（如 050025 博时标普500ETF联接）**：纯场内 ETF（51/15 开头）无场外直申，对应场内 = 其跟踪的 ETF → `online_code = 513500`（博时标普500ETF）。溢价率 = ETF 场内价 vs ETF 自身净值。这告诉我们：买联接（按净值，若开放）还是买 ETF（按溢价）更便宜。
- 映射在 `constants.py` 手工维护（联接 → ETF 关系稳定，不靠自动推断）。

**数据源（均已实测可达）**：
- **场内实时价**：新浪行情 `https://hq.sinajs.cn/list=<市场><代码>`（直连，GBK 解码，需 Referer `https://finance.sina.com.cn/`）。返回 `var hq_str_xxx="名称,今开,昨收,实时价,最高,最低,...,日期,时间,状态"`。**已实测** `sz161125`/`sz161130`/`sh513500`/`sh513100` 全部 200；字段[2]=昨收、字段[3]=实时价（盘前/非交易时段为 0，此时用昨收）。
- **最新单位净值**：东财 `https://api.fund.eastmoney.com/f10/lsjz?fundCode=<online_code>&pageIndex=1&pageSize=1`（代理，Referer `fundf10.eastmoney.com`）。返回 JSON：`DWJZ`(单位净值)、`FSRQ`(净值日期)、`JZZZL`(日涨跌%)，及 `SGZT`/`SHZT`。**已实测** 161125→DWJZ=3.1422(2026-10-27)、161130→4.4324、513500→2.4532、513100→1.9836。
- ⚠️ 东财 `fundgz` 估算净值接口经实测 404 失效，改用 `lsjz`（更强，且含净值日期与申赎状态）。
- ⚠️ 东财 `push2` 溢价率字段在沙盒被网络拦截；本模块改为**自行计算**，更可控：

**溢价率公式**：
```
溢价率(%) = (场内价 − 最新单位净值) / 最新单位净值 × 100%
场内价 = 实时价(字段[3]) 若 >0 否则 昨收(字段[2])
```
- 溢价率 > 0：场内比净值贵（买场内亏溢价，优先场外按净值买）；< 0：场内折价（场内更便宜）。
- 数值口径：基于「T-1 披露净值 + 当日场内价」的**静态溢价率**，是 LOF/ETF 通行的折价率定义；若后续需盘中 IOPV 精确值，再补东财 IOPV 源。

**开发细节**：
1. `fetch_premium()`：遍历 `FUND_POOL` → 取 `online_code` → 新浪场内价 + 东财净值 → 算溢价率 → 写 `qdii_premium`（date/online_code/premium_pct/market_price/nav/nav_date）。
2. **调度**：在 **14:30 北京时间、按 A 股交易日**触发（14:30 处于 A 股交易时段内，场内价为实时价；LOF/ETF 均在 A 股市场交易）。该任务与 SIGNAL（14:30、美股交易日）同槽，由 `qdii-cron` 文件锁串行化，互不抢写；若当日非 A 股交易日则跳过。
3. 前端按「溢价率」排序：折价（<0，绿/便宜）置顶提示「场内更划算」；高溢价（>3%）标红提示「限购抢手/场外更优」。

```sql
  online_code TEXT,               -- 对应场内代码
  market_price REAL,              -- 场内价(实时价或昨收)
  nav REAL, nav_date TEXT,        -- 最新单位净值 + 净值日期
  premium_pct REAL,               -- 溢价率(%)，>0溢价/<0折价
  source TEXT, fetched_at TEXT,
  UNIQUE(date, code)
);

-- 决策输出（每日）
CREATE TABLE qdii_decision (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  date TEXT, code TEXT, strategy TEXT,
  suggested_multiple REAL, reason_json TEXT,
  UNIQUE(date, code)
);

-- 元信息
CREATE TABLE qdii_meta (k TEXT PRIMARY KEY, v TEXT);
```

## 6. 调度设计（`qdii/scheduler.py`）

复用现有 `scheduler.py` 模式（纯标准库、20s 轮询、文件锁互斥、超时杀），但**独立实例、独立锁路径**（避免与 ntt-cron 抢同一 `.sync.lock`）。

- **限额/状态/费率/跟踪误差任务（LIMIT）**：`QDII_SCHED_LIMITTIMES`（默认 `09:00` 北京时间），**按 A 股交易日**触发（`is_a_share_trading_day()`）。
- **美股信号任务（SIGNAL）**：`QDII_SCHED_QDIITIMES`（默认 `06:30` UTC = `14:30` 北京时间），**按美股交易日**触发（`is_us_trading_day()`）。⚠️ 不能用现有的 `SCHED_FULL_WEEKDAY_ONLY`（那是 A 股周六日逻辑，与美股节假日不同）。
- 美股交易日历：项目零依赖，倾向**内置年度美国联邦节假日表**（`constants.py` 维护 2026/2027 列表 + 周末判断），不引第三方库。
- 启动即跑一次（`SCHED_RUN_ON_START=1`），空库从 `qdii/docs/data.json` 种子恢复。

### 14.3 折算溢价（2026-10-29 下午新增，v2.2.0）

**问题**：溢价率原来直接用（场内价 − 最新净值）/ 最新净值。QDII 净值 **T+1 披露**、遇海外休市还顺延，净值日期常比场内价晚 1~2 个交易日，这几天的指数涨跌被整段算进溢价，读出来的数字既不是溢价也不全是滞后。

**做法**：折算净值 = 最新净值 × 指数从「净值日期」到「最新收盘日」的累计涨幅；折算溢价 =（场内价 − 折算净值）/ 折算净值。
- `constants.PREMIUM_ETFS[*].bench` 声明每只 ETF 的指数源：纳指类 `("sina_us", ".NDX")`、标普类 `("sina_us", ".INX")`、日经 `("sina_fut", "NK")`、DAX `("em_us", "100.GDAXI")`。
- `fetcher_premium.index_cum_ratio(bench, nav_date)` 返回 `(ratio, asof)`；任一环节失败返回 `(None, None)`，该行折算列留空、提示列回退原口径，**绝不因缺数据而整行丢失**。
- 落库新增 4 列：`est_nav` / `est_premium_pct` / `bench_label` / `bench_asof`（旧库由 `init_db` 的 ALTER 迁移补列）。
- 前端：列改为「场内代码 / ETF名称 / 场内价 / 净值·日期 / 溢价率 / 折算溢价 / 提示」，删除「跟踪指数」独立列（并入名称小字），列数由 8 降到 7 以适应半宽卡片。

**日经为什么走新浪外盘期货**：东财 `100.N225` / `100.GDAXI` 在本网络恒被断（RemoteDisconnected，直连与代理皆然），而新浪 `GlobalFuturesService.getGlobalFuturesDailyKLine?symbol=NK` 可稳定返回日线。日经用 **NK 期货**近似现货（24h 连续、含次日盘前），折算误差 <0.5%，对 5% 量级的溢价够用；**DAX 无任何可达日线源，折算列恒空**（该 ETF 溢价仅 1% 上下，影响可接受）。

**关键实测结论（务必写进汇报）**：折算前后差距只有 **0.3~0.9 个点**——纳指类 15.45%→14.82%、13.90%→13.29%，标普类 9.57%→9.27%，日经 5.17%→4.27%。可见 **14% 的溢价是真实溢价（QDII 额度紧张、申购受限、场内抢筹），不是 T+1 滞后造成的**。此前页面写「溢价率会被系统性高估十几个点」是错的判断，已随本节一并更正。

**未纳入的因素**：汇率日内波动（美元资产对人民币，纳指/标普类同向同幅，影响通常 <0.2%）、申赎费用、ETF 折溢价套利机制失效时的溢价粘性。

**测试**：QDII 29 → 35 项（新增 `PremiumAdjustedTest` 6 项：区间涨幅、净值已最新时 ratio=1、缺参数/源失效返回 None、折算溢价必低于原口径且差额符合公式、每只 ETF 必须声明 bench）。

|---|---|---|---|---|---|

设计要点：
- **不能用加权平均合并**：VIX 是恐慌的「结果」、美债是压制估值的「原因」，两者可以同时出现也可以单独出现，任一极端都足以减半 → 并列（OR）。同时触发只乘一次 0.5，不叠加。
- **修掉一个归因 bug**：旧实现把两者塞进同一句、且只输出 VIX 数值，于是美债触发时会写「避险升温（VIX 15.0）→ ×0.5」——一个低于 30 阈值的数字却减了半，看着就是算错。改为 `risk_off_assess()` 返回 `(系数, 触发项[], 预警项[])`，**谁触发写谁**（`避险防御 ×0.5：美债10Y 单日上行 +35bp 超 30bp（利率冲击）`）。逐基金 `recommend()` 与大类 `recommend_category()` 共用同一函数，避免两处逻辑漂移。
- **新增三档软阈值**：`risk_off_vix_warn=20`、`risk_off_vix_jump=20`、`risk_off_ust_warn_bp=15`。原来是一刀切，逼近过程完全看不见；现在理由里会出现「VIX 25.0 处于 20~30 预警区（未达防御阈值，不减额）」。
- **未触发时也写当日取值**：`避险指标正常：VIX 16.9（阈值 30）、美债10Y 单日 -5bp（阈值 +30bp）`。否则判据只在触发那天出现，用户无从判断策略到底有没有在用它们。
- 面板同步：VIX 行副标题「日频 · 上一交易日收盘 · 防御阈值 30」、美债行「实时 · 收益率 · 防御阈值 日升 30bp」；触发时名字后面直接挂 `已触发防御 ×0.5` / `预警区` / `逼近阈值` 徽标；顶部黄色提示条一并更正（原文写「现货/美债为上一交易日非实时」，而美债其实是真的实时）。
